The brief

The homework, as given at the end of Monday's lecture:

Create a personal portfolio repo on GitHub called ‘portfolio’. Add index.html with your name, photo, bio, skills, and links to 2–3 course projects. Make at least 5 meaningful commits with clear messages (e.g., ‘Add hero section’, ‘Add project cards’, ‘Fix mobile layout’). Submit your GitHub repo URL on Cybercampus by Wednesday.

— Git.pdf, Week 10 · Summary & Homework

Starting the repo

The repo is a folder with a hidden .git/ directory inside it. git init -b main creates that folder and names the first branch main in one step; the homework's examples push to main, so starting there saves a rename later. 

# create the project folder and start tracking it
$ mkdir portfolio && cd portfolio
$ git init -b main
Initialized empty Git repository in …/web-prog-gachon/portfolio/.git/
$ git status --short --branch
## No commits yet on main

The add → commit cycle

Every change went through the three states from the lecture: the working directory, the staging area (git add queues exactly what the next commit should contain), and the local repository (git commit saves the snapshot). Nothing is online at this point — commits are local until git push.

Each commit stages only the files for one feature, which is what keeps every message honest: 

# 1 — one feature at a time: stage it, commit it
$ git add README.md .gitignore
$ git commit -m "Initial commit: add README and .gitignore"

# 2 — the page shell: header, nav, main, footer
$ git add index.html
$ git commit -m "Add semantic HTML page structure"

# 3 — name, photo, bio, and the two call-to-action buttons
$ git add index.html img/avatar.svg
$ git commit -m "Add hero section with photo and bio"

# 4 — Book Search App, registration form, Team 16 proposal
$ git add index.html

What's left: publishing the repo

The history is complete but entirely local. Publishing is two commands once the repo exists on GitHub — created with the exact name portfolio and left public, since private repos block GitHub Pages on the free plan: 

# create the repo on GitHub named exactly "portfolio", then:
$ git remote add origin https://github.com/<username>/portfolio.git
$ git push -u origin main

git remote add links the local repo to GitHub under the nickname origin; git push -u origin main uploads the commits and remembers the upstream, so later pushes are a plain git push. After that, the repo URL is what gets submitted on Cybercampus — and the same repo is what the deployment homework (GitHub Pages + Lighthouse) will build on.

What the exercise taught

  • Git and GitHub are different layers: eleven commits existed and the history was already readable long before anything is online — Git tracks locally, GitHub hosts remotely.
  • The staging area is what makes messages truthful: staging only the files for one feature means git commit -m can say exactly what that commit does.
  • Small, named commits read like a changelog — the homework's own examples (“Add hero section”, “Fix mobile layout”) turned out to be natural commit boundaries.
  • git log --oneline plus git status --short is the fastest way to answer “where am I, and what happened?”.
