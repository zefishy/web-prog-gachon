The four components

The rule from the slides: one component, one responsibility. The screen is one box; each box in the mockup is one component; and each component is small enough to read in a single glance. What follows is the actual TypeScript source, verbatim from the repository.

Projects — the parent that owns the filter

Projects is the only component with state. The filter is a string, useState keeps it, and every render derives both the button list (one per technology, deduplicated with a Set) and the visible projects from the full data. Nothing else in the tree needs to know the filter exists — only FilterBar changes it and ProjectList renders the result. The three project objects live here too, so adding a fourth project is one more object and nothing else.

src/components/Projects.tsx

import { useState } from "react";
import FadeIn from "./FadeIn";
import ProjectCard from "./ProjectCard";
import ProjectList from "./ProjectList";
import FilterBar from "./FilterBar";

interface Project {
  title: string;
  description: string;
  tech: string[];
  liveUrl?: string;
  repoUrl?: string;
  image?: string;
}

const projects: Project[] = [
  {

    tech: ["Python", "Flask", "Supabase", "Stripe"],
    liveUrl: "#",
    repoUrl: "https://github.com/zefishy/wdp",
    image: "/e-commerce-app.png",
  },
  {
    title: "Discord Bot with DiscordJS",
    description:
      "I developed a discord bot with DiscordJS to handle simple administrative functions",
    tech: ["JavaScript", "DiscordJS"],
    repoUrl: "https://github.com/zefishy/discord-bot",
    image: "/discord-bot.png",
  },
  {
    title: "Web Programming Library",
    description:
      "A static HTML/CSS/JS coursework library with per-week exercise folders, themed spines, and accessibility-focused design.",
    tech: ["HTML", "CSS", "JavaScript"],
    liveUrl: "https://zefishy.github.io/web-prog-gachon/",
    repoUrl: "https://github.com/zefishy/web-prog-gachon",
    image: "/web-prog-library.png",
  },
];

export default function ProjectsSection() {
  const [activeFilter, setActiveFilter] = useState<string>("All");

  const techs = [
    "All",
    ...Array.from(
      new Set(projects.flatMap((p) => p.tech))
    ).sort(),
  ];

  const filteredProjects = projects.filter((p) =>
    activeFilter === "All" ? true : p.tech.includes(activeFilter)
  );

  return (
    <section id="projects" className="section-container">
      <FadeIn>
        <p className="text-primary font-mono text-sm mb-2 tracking-wider uppercase">
          Projects
        </p>
        <h2 className="section-heading">My Projects</h2>
        <p className="section-subheading">
          Some Personal/Professional Projects I've Built Over the Years.
        </p>
      </FadeIn>

      <FilterBar
        techs={techs}
        activeFilter={activeFilter}
        onFilter={setActiveFilter}
      />

      <ProjectList projects={filteredProjects} />
    </section>
  );
}

FilterBar — a row of buttons, no memory

FilterBar receives the list of technologies (already including All), the active one, and a function to call when one is chosen. It holds no state of its own: it draws what it is given and reports clicks. The active button is styled by the parent’s comparison, not by local bookkeeping.

src/components/FilterBar.tsx

interface FilterBarProps {
  techs: string[];
  activeFilter: string;
  onFilter: (filter: string) => void;
}

export default function FilterBar({
  techs,
  activeFilter,
  onFilter,
}: FilterBarProps) {
  return (
    <div className="flex flex-wrap gap-2 mb-6">
      {techs.map((tech) => (
        <button
          key={tech}
          onClick={() => onFilter(tech)}
          className={`px-4 py-2 rounded-full border text-sm transition-colors ${
            activeFilter === tech
              ? "bg-primary text-primary-foreground"
              : "border-border text-muted-foreground hover:bg-secondary"
          }`}
        >
          {tech}
        </button>
      ))}
    </div>
  );
}

ProjectList — array in, elements out

ProjectList is a thin map. The key comes from the data’s title, never the array index, so React can match a card before and after a filter change. Each card also gets a staggered entrance via the FadeIn wrapper.

src/components/ProjectList.tsx

import FadeIn from "./FadeIn";
import ProjectCard from "./ProjectCard";

interface ProjectListProps {
  projects: Project[];
}

interface Project {
  title: string;
  description: string;
  tech: string[];
  liveUrl?: string;
  repoUrl?: string;
  image?: string;
}

export default function ProjectList({ projects }: ProjectListProps) {
  return (
    <div className="grid grid-cols-1 md:grid-cols-2 gap-6">
      {projects.map((project, i) => (
        <FadeIn key={project.title} delay={i * 0.1}>
          <ProjectCard
            title={project.title}
            description={project.description}
            tech={project.tech}
            liveUrl={project.liveUrl}
            repoUrl={project.repoUrl}
            image={project.image}
          />
        </FadeIn>
      ))}
    </div>
  );
}

ProjectCard — everything comes from props

The card knows nothing about projects in general. It receives one object’s fields, prints them, and links out. The image and the links are rendered conditionally, so a project without a demo link or a screenshot still renders a valid card.

src/components/ProjectCard.tsx

import { ExternalLink, Github } from "lucide-react";
import { Badge } from "./ui/badge";

interface ProjectCardProps {
  title: string;
  description: string;
  tech: string[];
  liveUrl?: string;
  repoUrl?: string;
  image?: string;
}

export default function ProjectCard({
  title,
  description,
  tech,
  liveUrl,
  repoUrl,
  image,
}: ProjectCardProps) {
  return (
    <div className="glass-card h-full flex flex-col">
      {image && (
        <div className="rounded-lg overflow-hidden mb-4 bg-secondary/50 aspect-video">
          <img src={image} alt={title} className="w-full h-full object-cover" />
        </div>
      )}
      <h3 className="font-semibold text-lg mb-2">{title}</h3>
      <p className="text-muted-foreground text-sm mb-4 flex-1">{description}</p>
      <div className="flex flex-wrap gap-2 mb-4">
        {tech.map((t) => (
          <Badge key={t} variant="secondary" className="text-xs">
            {t}
          </Badge>
        ))}
      </div>
      <div className="flex gap-3">
        {liveUrl && (
          <a
            href={liveUrl}
            target="_blank"
            rel="noopener noreferrer"
            className="inline-flex items-center gap-1.5 text-sm text-primary hover:underline"
          >
            <ExternalLink className="w-4 h-4" /> Live Demo
          </a>
        )}
        {repoUrl && (
          <a
            href={repoUrl}
            target="_blank"
            rel="noopener noreferrer"
            className="inline-flex items-center gap-1.5 text-sm text-muted-foreground hover:text-foreground transition-colors"
          >
            <Github className="w-4 h-4" /> Source Code
          </a>
        )}
      </div>
    </div>
  );
}

How the filtering works

  • State lives at the top. Projects remembers one string, the selected technology. The homework slides introduce useState next week; filtering needs one piece of state, so this is the one hook the gallery uses.
  • Derived, not stored. The visible list and the button list are both computed from projects and activeFilter on every render. There is no second array to keep in sync — the filter cannot drift away from what is on screen.
  • Callbacks go down, data comes back up. FilterBar calls onFilter(tech). That is the setter from Projects. React re-renders it, which re-renders both children with new props. No component beneath Projects ever edits another component’s data.
  • A stable key keeps card identity. Filtering removes cards; the title lets React remove exactly the right ones. An index key would re-number the survivors and can leave stale DOM behind.
  • All of it is one screen built from small parts. Projects could be inlined into one long function, but then the filter logic, the buttons, the list and the card would all be tangled together. Four components keep each job testable on its own.
