The four components

The rule from the slides: one component, one responsibility. The screen is one box; each box in the mockup is one component; and each component is small enough to read in a single glance.

App — the parent that owns the filter

App is the only component with state. The filter is a string, useState keeps it, and every render derives the visible projects from the full list. Nothing else in the tree needs to know the filter exists — only FilterBar changes it and ProjectList renders the result.

src/App.js

import { useState } from 'react';
import FilterBar from './components/FilterBar';
import ProjectList from './components/ProjectList';
import { projects } from './data/projects';
import './App.css';

const FILTERS = ['All', 'JavaScript', 'CSS', 'HTML'];

export default function App() {
  const [filter, setFilter] = useState('All');

  const visible =
    filter === 'All'
      ? projects
      : projects.filter((project) => project.tech.includes(filter));

  return (
    <div className="gallery">
      <header className="gallery__header">
        <h1 className="gallery__title">Ryan's projects</h1>
        <p className="gallery__lead">
          Coursework from the Web Programming Library, filtered by the
          technology each project uses.
        </p>
      </header>

      <FilterBar filters={FILTERS} active={filter} onChange={setFilter} />

      <p className="gallery__count" aria-live="polite">
        {visible.length} of {projects.length} projects
      </p>

      <ProjectList projects={visible} />
    </div>
  );
}

FilterBar — a row of buttons, no memory

FilterBar receives the list of filters, the active one, and a function to call when one is chosen. It holds no state of its own: it draws what it is given and reports clicks. aria-pressed tells assistive technology which button is selected without inventing a custom widget.

src/components/FilterBar.js

export default function FilterBar({ filters, active, onChange }) {
  return (
    <div
      className="filter-bar"
      role="group"
      aria-label="Filter projects by technology"
    >
      <span className="filter-bar__label" aria-hidden="true">
        Technology
      </span>
      {filters.map((filter) => (
        <button
          key={filter}
          type="button"
          className="filter-bar__btn"
          data-filter={filter}
          aria-pressed={filter === active}
          onClick={() => onChange(filter)}
        >
          {filter}
        </button>
      ))}
    </div>
  );
}

ProjectList — array in, elements out

ProjectList is a thin map. The key comes from the data’s id, never the array index, so React can match a card before and after a filter change. When the filter matches nothing it returns a message instead of an empty grid.

src/components/ProjectList.js

import ProjectCard from './ProjectCard';

export default function ProjectList({ projects }) {
  if (projects.length === 0) {
    return <p className="gallery__empty">No projects use that technology yet.</p>;
  }

  return (
    <ul className="project-grid">
      {projects.map((project) => (
        <li key={project.id}>
          <ProjectCard {...project} />
        </li>
      ))}
    </ul>
  );
}

ProjectCard — everything comes from props

The card knows nothing about projects in general. It receives one object’s fields, prints them, and links out. The links are rendered conditionally, so a project without a demo link still renders a valid card.

src/components/ProjectCard.js

export default function ProjectCard({
  title,
  description,
  tech,
  github,
  demo,
}) {
  return (
    <article className="project-card">
      <h2 className="project-card__title">{title}</h2>
      <p className="project-card__desc">{description}</p>

      <ul className="chips" aria-label="Tech stack">
        {tech.map((item) => (
          <li key={item}>{item}</li>
        ))}
      </ul>

      <p className="project-card__links">
        {github && (
          <a href={github} rel="noopener noreferrer">
            GitHub
          </a>
        )}
        {demo && (
          <a href={demo} rel="noopener noreferrer">
            Live demo
          </a>
        )}
      </p>
    </article>
  );
}

How the filtering works

  • State lives at the top. App remembers one string, the selected technology. The homework slides introduce useState next week; filtering needs one piece of state, so this is the one hook the gallery uses.
  • Derived, not stored. The visible list is computed from projects and filter on every render. There is no second array to keep in sync — the filter cannot drift away from what is on screen.
  • Callbacks go down, data comes back up. FilterBar calls onChange(filter). That is the setter from App. React re-renders App, which re-renders both children with new props. No component beneath App ever edits another component’s data.
  • A stable key keeps card identity. Filtering removes cards; the id lets React remove exactly the right ones. An index key would re-number the survivors and can leave stale DOM behind.
  • All of it is one screen built from small parts. App could be inlined into one long function, but then the filter logic, the buttons, the list and the card would all be tangled together. Four components keep each job testable on its own.

Running and submitting

The source beside this page is CRA-shaped: it has public/index.html, src/index.js and one file per component, so it runs unchanged after the two commands below. It is not built or committed here — the submission is the repo URL itself.

In the project folder

cd week11/portfolio-gallery
npm install
npm start        # http://localhost:3000

Submit the GitHub repository URL on Cybercampus before next class. The three props rules from the slides still apply: props flow one way, every list item needs a unique stable key, and small components compose into bigger ones.
