Fix the slow page

Five small edits to a slow page. For each one you get the line before, the line after, why it helps, and the Lighthouse metric that should move.

The slow page

Here is a small cafe page with five common loading mistakes. Each fix below shows the line as it stands now, the same line fixed, why the change helps, and which Lighthouse metric it moves. Work through them on a copy of your own page, then run Lighthouse before and after. 

<!DOCTYPE html>
<html>
<head>
  <meta charset="UTF-8">
  <title>Café Corner</title>
  <script src="js/app.js"></script>
  <link rel="stylesheet" href="css/site.css">
</head>
<body>
  <div class="hero-banner"> ... </div>
  <img src="img/hero.jpg" alt="Latte art">
  <img src="img/menu.jpg" alt="Menu board">
  <img src="img/shop.jpg" alt="Front of the shop">
</body>
</html>

This page is a hands-on companion to the explainer, which covers how to read the report. The metrics named here (FCP, LCP, TBT, CLS) are the ones defined in the performance slides.

Fix 1 — Add defer to the script

A classic <script src> in the head stops the HTML parser until the file has downloaded and run, so nothing below it can paint. defer lets the download happen in parallel and runs the script after the document is parsed, in order.

Before

<script src="js/app.js"></script>

After

<script src="js/app.js" defer></script>

Moves: First Contentful Paint and Largest Contentful Paint (the render-blocking audit), and Total Blocking Time if the script is heavy.

Fix 2 — Give every image a width and height

Without dimensions the browser does not know how much room an image needs, so the text below jumps down when the file arrives. The two attributes give it the aspect ratio before the download starts. The CSS keeps the image fluid.

Before

<img src="img/shop.jpg" alt="Front of the shop">

After

<img src="img/shop.jpg" alt="Front of the shop" width="800" height="450">

/* in site.css */
img { max-width: 100%; height: auto; }

Moves: Cumulative Layout Shift. This is the one fix that has no effect on load speed, only on stability.

Fix 3 — Lazy-load images below the fold

The menu and shop photos are off-screen on first load. Marking them loading="lazy" stops them competing for bandwidth with the hero. Do not put it on the hero image itself: that delays the largest element on the page.

Before

<img src="img/menu.jpg" alt="Menu board">
<img src="img/shop.jpg" alt="Front of the shop">

After

<img src="img/menu.jpg" alt="Menu board" width="800" height="450" loading="lazy">
<img src="img/shop.jpg" alt="Front of the shop" width="800" height="450" loading="lazy">

Moves: Largest Contentful Paint and Speed Index (less competing for bandwidth) and total bytes transferred on load. Lighthouse lists the images it could have deferred under its offscreen-images diagnostic.

Fix 4 — Mark the hero image fetchpriority="high"

Browsers guess an image’s priority until layout tells them how big it is. The hero is the largest element on screen, so say so up front. Together with fix 3 this is the pair: lazy for what is not needed yet, high for what is needed first.

Before

<img src="img/hero.jpg" alt="Latte art">

After

<img src="img/hero.jpg" alt="Latte art" width="1200" height="600" fetchpriority="high">

Moves: Largest Contentful Paint. The related Lighthouse insight is about the LCP image being discovered early and given high priority.

Fix 5 — Preload what the page needs early

A web font is only discovered after the CSS has downloaded and been parsed, so the text waits. A rel="preload" link in the head starts the download at once. Fonts need crossorigin even on the same origin, or the file is fetched twice. The same idea works for an image used as a CSS background, with as="image".

Before

<link rel="stylesheet" href="css/site.css">
/* site.css: @font-face { src: url(../fonts/inter.woff2) } */

After

<link rel="preload" href="fonts/inter.woff2" as="font" type="font/woff2" crossorigin>
<link rel="stylesheet" href="css/site.css">

Moves: First Contentful Paint and LCP when the largest element is text or a late-discovered image, and layout shift caused by the font swap.

Preload only a few critical files. Each preload is a bet that the file really is needed on this page; a preloaded file that goes unused produces a console warning.

Two extras Lighthouse checks in the same run

These do not change the Performance number. They are in the Accessibility category, but the slow page above has both problems and each is a one-line fix.

Before

<html>
...
<body>
  <div class="content"> ... </div>

After

<html lang="en">
...
<body>
  <main id="main"> ... </main>

Moves: the Accessibility audits for a lang attribute on <html> and for a main landmark, so screen readers pick the right pronunciation and can jump straight to the content.
